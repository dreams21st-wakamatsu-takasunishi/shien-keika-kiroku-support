# 施設共通ログインと一般職員選択

2026-10-30追記：入力画面はメール・職員IDと同じ共通ログイン欄へ統一しました。施設共通ログインの承認・職員選択・権限制限は維持しています。現在の入口・ID重複対策は[共通ログイン欄](unified-login.md)を参照してください。

更新日: 2026-10-15

ユーザーの決定により、施設ログイン後の一般職員選択には個人PINを要求しない。他人名義を選択できる運用リスクを受容し、現場の操作負担を優先する。職員選択は本人認証ではなく、本人確認強度が従来と同等であるとは説明しない。

選択後はその一般職員の既存Authセッションになるため、表示名だけの変更ではなく、そのアカウントに許可された操作が可能になる。施設の資格情報を知る職員を信頼する運用が必要。個人のパスワード認証と同じ本人保証にはならず、退職時の共通パスワード変更と利用停止、特別権限を付与する前の本人メール・個人パスワードの再確認が必要である。

## 利用開始

管理者が個人のメール＋パスワードで入り、「職員 → 端末・アクセス → 施設共通ログイン」で設定する。

1. 端末承認を有効にし、利用するブラウザーを施設共用端末として承認する。個人端末・未登録・承認待ち・取消済みでは共通ログインできない。新しい経路から端末を自動承認しない。
2. 既存の事業所コードを確認し、施設IDと共通パスワードを管理者が設定する。パスワードは12文字以上、UTF-8で72バイト以内（bcryptの切り捨て回避）。共通パスワードは画面再表示できない。変更時は入力し直す。
3. 「施設共通ログインを有効にする」と職員選択のリスク確認をチェックして保存する。設定保存は楽観revisionで競合検出し、利用中の施設ログインと選択途中の要求を失効させる。

実事業所では初期状態は未設定・無効。共通IDやパスワードを開発側で勝手に決めたり、既存の職員パスワードを変更したりしない。従来の職員IDログインは移行用に残す。

一般職員は「事業所コード・施設ID・共通パスワード → 職員を選択」でログインする。PIN不要。共通認証だけではAuthセッションも児童情報も返さず、職員名と選択用UUIDだけを返す。対象は既存の職員名簿と一意に紐づく在籍・有効な一般職員アカウント。一般職員の個人メールアカウントにも対応する。未紐づけの名簿だけから自動でAuthを作らない。

管理者・教室長・児発管等は共通ログインの選択対象外。共通ログインを有効にした事業所では、特別権限の職員ID・QR・OTPだけのセッションからの特別権限利用も拒否する。個人メールとパスワードによるログインを使う。二段階認証を設定した一般職員も共通ログインで迂回しない。

特別権限アカウントに内部の職員ID用メールしかない場合は、有効化を拒否する。先に既存アカウントの個人メールログインを整備する。既存のAuth・名簿を削除して作り直す対応はしない。

## 認証・権限

- 施設の資格情報はservice_role限定のfacility_login_credentialsでbcrypt（cost 10）として保管する。ブラウザーの保存領域に共通パスワード・選択ticketを保存しない。事業所コードのみ任意保存する。ブラウザー自身のパスワード保存機能とは別。
- 資格情報の検証前に事業所・端末トークンのハッシュ・承認・facility_shared・端末承認ポリシーを検証する。汎用エラーで事業所/ID/パスワード/端末の正否を個別に開示しない。
- 失敗回数は端末15分5回・事業所15分50回、成功要求も端末5分30回まで。失敗を例外でrollbackして回数が消える設計にしない。
- 選択ticketは暗号学的乱数32バイト、DBにSHA-256だけを保存し、5分・同一端末・同一資格情報revision・初回の候補アカウントに固定する。選択時に在籍・紐づけ・role=staff・設定・端末を再確認し、一度だけ消費する。
- Edge Functionは選択した既存Authをサーバー側で解決する。無効化・削除・匿名/SSO・初期パスワード未設定・MFAを検証する。管理APIによる一回限りのサーバー内交換でセッションを得る。メールを送信せず、交換用リンクやトークンをブラウザーへ返さない。既存Auth UUID・個人パスワード・名簿IDは変更しない。
- 発行したAuthのsession_idをfacility_login_sessionsへ登録してからセッションを返す。最大12時間、共通資格情報revision・端末・選択職員に固定する。応答前の確定に失敗した場合はセッションを返さず、可能な限り失効処理する。失敗後は施設認証からやり直す。
- current_organization_id / current_user_roleに新しいセッション検査を加える。リフレッシュ後も同じsession_idに制限を適用する。別端末へJWTだけをコピーしてもDB参照できない。個人端末の制限や旧共有ログインの例外を新経路へ流用しない。
- 端末取消・設定変更/無効化・期限切れ・職員停止/権限昇格/紐づけ変更・Auth停止/MFAでは、その施設セッションのDBアクセスを拒否する。サービス権限を使う招待・職員管理・AI/経路・通知FunctionもDBのセッション検査を確認し、昇格後の古い施設セッションを使って管理APIを呼べないようにする。
- ブラウザーは表示復帰時と60秒ごとに状態を確認する。失効が確定すればログアウトする。通信不能時に表示中の画面を遠隔消去できる保証はない。サーバーへの取得・保存拒否と、ブラウザー上の表示消去を混同しない。
- 端末識別はブラウザー内の秘密トークンであり、ハードウェア認証ではない。端末トークンとセッションの両方を盗まれた場合まで防ぐものではない。

## 記録と互換性

facility_login_challenges / facility_login_sessionsに施設認証日時、端末、選択された名簿・既存Auth、発行日時、revision、期限を保管する。合言葉・個人PIN・Authリフレッシュトークンは記録しない。「選択された職員」は実際に操作した本人を証明しない。記録・下書き等の既存の個人IDによる所有を共通Authへ置き換えない。

セッション記録はアクセス制限の証拠でもある。Authトークンが有効なまま記録だけを削除すると旧セッション扱いへ戻るため、単に期限切れだからと削除しない。端末や職員を通常の管理画面で削除しても履歴を残し、参照先が消えたセッションは許可しない。事業所そのものを削除する場合は関連データとともに削除される。

資格情報が未設定/無効な事業所の既存ログインは維持する。児童アカウント、Dレッスンのログイン、学習記録、既存の職員パスワードやメールアドレスはこの展開で変更しない。
