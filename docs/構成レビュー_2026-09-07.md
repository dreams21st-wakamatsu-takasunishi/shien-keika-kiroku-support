# 構成レビューと保守方針（2026-09-07）

## 確認した範囲

アプリの起点から画面・共通処理への参照関係、保存境界、更新処理、PDF出力、依存パッケージ、公開時の検証手順を確認した。全業務の本番操作・全SQLの監査を完了したという意味ではない。

## 今回実施した整理

### 未使用部分

- アプリからの参照がない `DailyChildPlanDialog.tsx` を削除した。利用予定の現行編集画面、予定データ、DBは削除していない。
- ルートアプリで使われていない `express`、`dotenv`、`@types/express`、`autoprefixer`、直接指定の `esbuild` を整理した。必要なビルド内部の依存は残る。
- Viteの重複指定を除き、ビルド用プラグインとLeaflet型定義を開発依存へ移した。
- 存在しないルートの `server.js` を削除対象にしていた旧 `clean` コマンドを廃止した。
- `放課後等デイサービス-マニュアル確認/` は別アプリとして独自の依存定義を持つため、変更していない。
- 凍結中の個別支援計画・5領域は「未使用だから削除」とは扱わず、実装・保存データを保持した。

削除したソースと依存定義はGit履歴から復元できる。保存済みの児童・記録・予定の削除は行っていない。

### 読み込み負荷

PDFライブラリを出力操作時にだけ読み込む。初回のPDF出力中は既存の処理中表示を使い、読み込み失敗時は再試行・保存後の手動更新を案内する。失敗を理由に自動リロードしない。

同一条件のローカル試用用ビルドで、PDF変更前後の起動時JavaScriptを比較した。

| 指標 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 起動時JavaScript（非圧縮） | 2,250,514 bytes | 1,602,242 bytes |
| 同 gzip | 617,890 bytes | 422,813 bytes |

非圧縮で約29%削減。これは初期実行コードの比較であり、体感速度を29%改善したという測定ではない。オフライン用の事前キャッシュは全静的ファイルを取得するため、インストール時の総通信量が同じ比率で減るわけではない。

### 更新処理・キャッシュ

- 更新確認のロジックをReact画面から分離し、単独でテストできる構成にした。
- フォーカス復帰と表示復帰が重なっても、同じ更新確認を二重実行しない。
- 画面終了後の監視、通信、遅延リロードを停止する。
- バックグラウンドの更新発見・Service Worker切替ではリロードしない。更新・再読み込みは利用者の明示操作からだけ行う。
- 手動更新時のリロードを一回に制限し、遅れて二度目のリロードが起こらないようにした。
- キャッシュを公開パス単位で分離し、同じドメインにある別アプリのキャッシュを削除しない。
- ハッシュ付きの保存済み静的ファイルを読む際、不要な裏側の再取得を行わない。キャッシュが使えない場合も、オンライン取得は継続できる。
- 更新確認URLの時刻パラメーター付きレスポンスやAPIデータをキャッシュへ蓄積しない。
- 自アプリの新形式キャッシュは現行と直前2版を保持する。旧形式キャッシュは他アプリとの区別ができないため、一括削除しない。
- 通知選択時は、このアプリの既存画面にフォーカスを戻す。編集中の画面を再ナビゲーションして初期化しない。

キャッシュはバックアップではない。ブラウザによる削除や容量制限の影響を受ける。古い画面を何世代も開き続けた場合の動作まで保証するものではなく、更新通知があれば入力内容を保存してから更新する。

## 検証方法

Node.js 24系（GitHub Actionsと同じ系統）で実行する。

```powershell
npm.cmd install
npm.cmd run check
```

`check` は型チェック、自動テスト、本番ビルドを順に実行する。GitHub Actionsにも自動テストを追加し、失敗時には公開処理へ進まない。

今回の確認結果：

- 型チェック・自動テスト31項目・本番ビルドが成功。
- 既存の朝礼共同編集テスト8項目は維持・成功。
- ブラウザでPDFコードが起動時には実行されず、出力時に読み込まれることを確認。
- 単日PDF（A4・1ページ）と月間PDF（表紙付き・2ページ）をダウンロードし、日本語・表・改ページを画像化して確認。
- 更新通知中も保存前のメモが残り、同時の表示復帰・フォーカス復帰からの更新確認が1回だけで、リロードが0回であることを確認。
- 390px、768px、1024px幅で記録確認画面と更新通知が画面全体の横はみ出しを起こさないことを確認。
- 事前キャッシュ済みのローカル検証データを使い、オフラインでのアプリ起動と月間PDF出力を確認。

ブラウザ検証は本番接続を無効にした隔離環境のサンプルデータで行った。本番DB・アカウント・保存済み記録への変更は行っていない。DBマイグレーションとEdge Functions再デプロイは不要。アプリ公開は別途GitHubへコミット・プッシュして行う。

## 次段階の候補

`App.tsx`、`RecordForm.tsx`、`dataService.ts`、月間予定・配車画面は依然として大きい。次は、保存処理を業務分野ごとに分け、記録入力の各項目を小さい部品へ分割すると保守しやすい。ただし、下書き・権限・配車時刻の連動があるため、各業務の回帰テストを先に増やしてから段階的に行う。

全画面の一斉遅延読込、大量の状態管理の置き換え、DBスキーマの整理は今回は実施していない。現状のビルドでも大きいチャンクの警告は残っており、アプリ全体の軽量化が完了したわけではない。
