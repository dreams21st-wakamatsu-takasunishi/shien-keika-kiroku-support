# 共通ログイン欄

2026-10-30。メール・職員ID・施設IDを「ログインID」「パスワード」に統一。QRログインと打刻のみの操作は別に残す。

## 認証と互換性

- `unified-login`は入力形式とservice専用`resolve_unified_login`で方式を一度だけ決定。失敗後に別方式へフォールバックしない。メールは従来と同じAuthパスワード認証、職員IDは従来のhandler、施設IDは既存の施設選択handlerを通す。
- 役職・所有者・対象Authをクライアントから指定できない。施設共通ログインの一般職員選択・5分ticket・12時間セッション・MFA/特別権限制限は変更しない。
- 施設IDを入力しても、未登録・承認待ち・利用停止・個人端末は施設共通ログインできない。端末の自動承認や共用化はしない。
- 事業所コードがない場合、サーバーで承認済みブラウザートークンの所属が一意であれば使用する。未登録・複数事業所所属等ならコード入力を求める。既存の保存済みコードは使い、別事業所への自動フォールバックはしない。メールでは不要。
- 同じ事業所の施設ID・職員IDの新規衝突をDBトリガーで拒否。既存の衝突は移行時に変更せず、そのIDの統一認証を汎用エラーで拒否する。管理者が個人メールで入りIDを整理する。失敗応答でIDの存在・役職・事業所名を返さない。
- パスワード・選択ticket・利用者一覧はアプリのlocalStorage/sessionStorageへ保存しない。非秘密の事業所コードだけを成功後に記憶する。セッションは従来のSupabase Auth方式を維持する。
- 個人職員IDのログイン・登録画面・管理Functionから独自の「10文字以上」条件を削除。ログイン時は空欄を拒否しAuthに検証を委ねる。新規設定はAuthの最低条件・最大72文字制限を維持。共通パスワード12文字・招待後初期設定条件は変更しない。既存パスワードは変更しない。

3. `unified-login`・`staff-login`・`manage-recorder-login`をデプロイ。
4. フロントエンド公開、公開版と資産・API疎通を確認。

旧`staff-login`・`facility-login`経路は旧ブラウザーの互換用に残す。廃止したのは方式別の入力画面であり、既存の認証権限やアカウントではない。GPSは導入しない。
