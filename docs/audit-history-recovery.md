# 監査履歴のHTTP 500対策（2026-10-16）

## 確認した現象

利用者が端末から書き出した診断情報4件は、いずれも `api.audit_logs` のHTTP 500。API要求からエラー記録までは約8.2秒。画面が `templates` の1件は、team画面で要求開始後、home、templatesへ移動してから失敗した履歴であり、テンプレート保存の失敗を示していない。

本番DBの認証ロールのstatement_timeout/lock_timeoutは8秒。従来の読み取り計画は直近30件のため約16,200行を走査し、行ごとに権限確認を評価、日時ソートを行っていた。読み取り専用のEXPLAIN ANALYZEでは実行約5,509ms、計画約103ms。端末の8秒失敗と併せて、監査履歴の検索負荷によるタイムアウトが主因と判断した。過去のレスポンス本文にはエラーコードが保存されていないため、過去4件すべてのSQLSTATEを直接確認できたわけではない。

## 修正

- `202610160002_audit_history_lookup.sql`：事業所・日時・IDの降順インデックスを追加。RLSの同一事業所・有効な権限・施設セッションの判定は維持し、安定関数をInitPlanで要求ごとに評価する。保存済みの監査行は変更・削除しない。
- 職員管理：監査履歴タブを開いたときだけ読込。同一事業所、日時降順・ID降順、30件、メタデータ列のみを明示。表示を離れた要求は中止し、古い応答は描画しない。取得失敗は「履歴なし」にせずエラーと再試行を表示する。
- 診断：許可リストのAPI名・要求開始画面・通信方式・有限の応答時間・既知のSQLSTATE等を保存する。生のメッセージ、本文、氏名、URL、トークン、要求／応答本文は保存しない。明示的なAbortErrorは偽の通信障害として記録しない。1件分を安全にコピーできる。
- 旧診断JSON v1はそのまま読み出す。未記録の項目を推測で復元しない。30日・200件の上限と端末内保存のみの方式は変えない。

## 検証方法

- `npm.cmd run check`：型検査、全回帰テスト、ビルド。
- `node scripts/check-audit-history-sql.mjs <PGlite runtime>`：架空16,001行、役職・組織・セッション・匿名アクセス、履歴保持、インデックスとInitPlanを確認。実データにアクセスしない。
- `node scripts/check-audit-history-ui.mjs --cli <playwright-cli.js>`：架空データのHTTP 500、再試行、画面遷移による要求中止、コピー、画面幅、非変更操作のみを確認。
- `npx.cmd supabase db query --linked --output json --file scripts/check-audit-history-query.sql`：本番の読み取り専用トランザクションで、既存管理者の通常権限をセッション内だけ模擬し、実行計画のみ取得する。認証アカウントや監査行の更新は行わず、最後にrollbackする。

## 適用・検証結果

2026-10-16、本番には002のインデックス・RLS評価方法の変更のみ適用。既存履歴の修正・削除、タイムアウトの延長は行っていない。同じ読み取り専用検証で実行約5,509ms → 8.008ms、計画約103ms → 10.301ms。走査は約16,200行＋ソートから、新しい事業所・日時インデックスで30行、権限確認のInitPlanは各1回に変わった。これはDB内の測定であり、端末からの通信時間は含まない。

隔離PostgreSQLの9項目と、架空データの画面23項目は成功。全334テスト・型検査・ビルドも成功。実在職員の更新／削除、支援記録や監査行の変更をテスト目的では実施していない。現場端末での再確認は別途必要。
