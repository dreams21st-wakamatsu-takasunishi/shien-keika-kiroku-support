# Dサポート・Dレッスン：無料枠での継続運用案

2026-11-13時点。目標は無料枠内での継続利用。新機能の前に、既存業務、データ保全、復旧の余裕を確保する。

## 根拠と判断基準

- 前回の請求期間：キャッシュなし10.928 GB（Dレッスン7.687 GB、Dサポート3.241 GB）。キャッシュあり0 GB。Dレッスンの約99.8%はデータベースAPI。処理ごとの過去のバイト数は未確定。
- 無料枠は[キャッシュあり・なしで別々に各5 GB](https://supabase.com/docs/guides/platform/manage-your-usage/egress)。余裕を3割残す社内目標は、各3.5 GB以下。前回のキャッシュなし実績からは約68%の削減が必要。Dレッスンだけを半減しても、Dサポートが同じなら約7.08 GB。両方を対象とする。
- 無料化判定では[DBサイズ・保存容量・関数・Realtimeなどの枠](https://supabase.com/docs/guides/platform/billing-on-supabase)と、[ログ取り込み](https://supabase.com/docs/guides/platform/manage-your-usage/logs-ingest)も別に確認。読み取り集計時点のDBサイズはDサポート150.68 MB、Dレッスン18.98 MB（無料枠500 MB／プロジェクト）。前回の関数実行は組織計43,015回、Realtimeは6,342メッセージ、ピーク7接続で各無料枠内。前回ログ取り込み64.886 GB（Dサポート64.491 GB）は転送量と別。公式掲載の無料枠は1 GB、課金開始は2027年初めまでの猶予後と案内されている。実際の適用条件を再確認し、発生元・ログ種別を絞る。監査履歴を削除したりログを一律停止したりしない。
- 無料には[毎日の自動バックアップがない](https://supabase.com/docs/guides/platform/backups)。DBだけでなく認証、ファイル、関数の復元手順と担当・暗号化保管先を決める。実データを書き出さないという既存の取り決めは変更しない。

## 改修の順序と機能への影響

| 優先 | 変更 | 職員・児童に見える変化 |
|---|---|---|
| 1（実装、本番未反映） | Word通知を未確認件数専用に分離。連携の校舎・所属・有効状態を軽い項目だけで照合し、連携児童の履歴・処理済み申請を通知のために取得しない。定期取得・自動再試行は行わない。 | ホームの「未確認件数を更新」を押した時点の件数と確認時刻を表示。新着は自動で増えない。申請一覧を開く・更新・閲覧・承認・差し戻しは維持。取得失敗を0件扱いしない。 |
| 2 | Dレッスンの児童ログインは本人・共通設定だけを取得。職員メニューの初回は児童の基本・進捗情報と最新の練習のみ、集計・履歴・出力や一括保存を伴う画面へ進むと詳細を取得。児童の保存は変更した項目を行の版付きで送信。 | 詳細取得に失敗した場合は画面を開き直す。別端末の変更を検出した場合は保存を停止。既存の集計・印刷・バックアップでは詳細を取得してから操作する。 |
| 3 | ホームの朝礼・勤怠・送迎便を当日分に限定し、各画面で指定日・週・月を追加取得。変更通知の日付で、関係しない取得済み期間の再取得を抑える。非公開の支援計画の読込は停止。 | 過去日は日付や月を指定して表示。未取得・取得失敗を「なし」と表示せず、データのないまま対象期間を編集・印刷しない。申し送りの関連便も日付指定。 |
| 4（実装） | Dレッスン連携ではDBから指定日の履歴だけを取得し、古い時刻表記は従来の判定へ渡す。自動取込で、児童・日付・連携版が同じ同時取得をまとめ、毎回の連携一覧再取得をサーバーでの連携版確認に置換。 | 取り込む内容は従来どおり。実績が増えたときの明示的な再取得を保持。 |
| 5（一部実装） | この端末の診断履歴で、同じAPI失敗が1分以内に続いた場合だけ初回・最終と回数をまとめる。Supabase側ログ量の原因特定・変更は別途。 | 画面に回数が残り、別種の失敗や監査履歴は変更しない。端末の診断整理はSupabase側のログ削減とは別。 |

公開順は Dレッスンの `support_learning_day_history.sql`・`lesson_staff_roster.sql`・`lesson_student_delta.sql` → Dレッスンの `support-learning-read`・`support-word-review` → Dサポートの `lesson-learning` → 両アプリの画面。旧画面で使っていたAPIは維持する。実績の差分は変更した最上位項目単位（例：練習履歴に変更があったときは、履歴項目を送る）。

プロジェクトの分割・統合、認証方式の入れ替え、過去履歴の削除、公開キャッシュに児童情報を置く方法は初手にしない。変更は一つずつ入れ、主な業務画面の再現試験と通信量の差を確認する。

## 実装：データ転送量の確認

管理者の「事業所の設定 → 職員・運営 → データ転送量」。公式Usageを開き、対象組織・請求期間・All projectsで表示した Egress と Cached Egress の数字を記録する。無料枠との比較、70%・85%・100%の警告、途中経過からの単純な期末見込み、最新24件を表示する。同じ請求期間・同じ確認日の訂正はその日の値を更新する。古い値は現在値と区別する。数字と日付だけを事業所ごとにブラウザへ保存し、クラウドには保存しない。

## Supabase側ログの切り分け

本番DBを読み取り確認した結果、両プロジェクトとも `log_statement=ddl`、`log_duration=off`、`log_min_duration_statement=-1`、接続・切断の記録はオフ、`pgaudit.log=none`（照会セッションでの値）。アプリ側の呼び出し集計ではDサポートの下書き関連、Dレッスンの児童行関連が目立つ。ただしDBの呼び出し数はログ取り込み容量ではない。

次は[Logs ExplorerのSQL](https://supabase.com/docs/guides/observability/advanced-log-filtering)で通常日・繁忙日の24時間を別々に指定し、本文を取得せずに発生元別の件数とメッセージサイズを比較する。監査履歴やログ設定は変更しない。メッセージのサイズは付帯情報を含まないため公式Usageとは一致しない。

```sql
select source, count() as events, sum(length(event_message)) as message_bytes
from logs
group by source
order by message_bytes desc
limit 20;
```

診断欄ではこのタブの既存のSupabase APIリクエストを許可済みの操作名・回数・失敗数・取得できた Content-Length だけで集計する。応答本文を読まず、計測用リクエストを追加しない。ヘッダーのない応答は不明、WebSocket・他端末・Dレッスン・サーバー間通信は対象外。合計は請求上の転送量ではなく、公式値へ足さない。

当面は公式値を週1回と繁忙日の後に記録する。目標3.5 GBを超える見込みになったら新機能より削減を優先し、85%から原因調査を急ぐ。無料へ戻す判断は、軽量化後の通常・繁忙を含む少なくとも1請求周期で各3.5 GB以下、その他の枠にも余裕、バックアップ・復元の運用が確立してから。アプリ側では自動ダウングレード・自動制限・課金設定変更をしない。
