# 読み込み・保存の軽量化（2026-10-16）

## 変更した処理

- Realtimeの更新通知に対応するデータだけを再取得。朝礼記録は1通信、送迎状況は職員名・車両名の依存情報を含め3通信。未知の通知、手動再読み込み、切断後の再接続では全取得して整合性を回復する。
- 支援記録の更新通知では通知に含まれたIDだけを読み直し、既存一覧に差し替える。削除・閲覧不可になったIDも一覧から除外する。更新前の画面を維持し、取得に失敗しても空の一覧へ置き換えない。
- 初回取得中の通知をテーブル単位でまとめ、全データの再取得を繰り返さない。最初の取得が終わった時点で全画面のローディングを解除する。
- トークン更新でプロフィール内容が同じ場合、データ取得・購読をやり直さない。ユーザー、権限、端末の利用範囲が変わった場合は旧取得結果を破棄する。
- 下書き一覧はJSONパスの選択取得で概要のみを読み、児童別の回答本文を取得しない。編集中の実際の下書き読み込み・版確認は維持する。
- 下書き一覧の重複取得をまとめ、正常なリアルタイム接続中の補助ポーリングを10秒間隔から60秒間隔に減らす。非表示タブでは補助ポーリングを休止する。接続障害時は10秒間隔、画面へ戻った時は即確認する。
- 保存直前の記録確認は3通信から1通信へ統合。全項目・版番号・削除済みIDを引き続き確認し、本文比較・承認済み記録の保護・楽観ロックは変更しない。
- ログインの事業所名・職員紐付け・端末権限の独立した確認を並列化する。施設アクセス確認後に実施し、必要な全確認が完了するまで画面には進まない。
- 記録入力・一覧・職員管理などは画面単位でコードを遅延取得する。取得失敗時に入力画面を自動更新しない。

## 処理時間の確認

「設定」→「エラー・操作履歴」→「処理時間の確認（このログイン中）」を開く。
「再読み込み」で直近・平均・最大・失敗回数を確認でき、「履歴を書き出す」でエラーと一緒に集計を保存できる。

計測は直近100件の端末メモリ内のみ。画面再読み込み・ログアウト・ユーザー切り替えでリセットする。固定の処理名・所要時間・成否以外を保存せず、本文、名前、ID、URL、トークン、API応答は含めない。サーバー・AIへの自動送信はない。
上書き比較でユーザーが確認している待ち時間を、保存通信の時間に含めない。

## 残る制約

初回は既存機能との整合性のため、支援記録の履歴を含め30種のデータを取得する。履歴のページングや期間指定取得は未実装。今回の変更だけで実機の10〜60秒が何秒になるかは保証せず、公開後に上記計測で評価する。
実データでの保存・アカウント変更を検証のために行わない。

## 2026-10-26：支援記録の読み取り権限判定

既存の事業所・日付／児童別インデックスは維持し、重複するインデックスは増設しない。`records_select` の事業所判定だけを `(select public.current_organization_id())` にし、既存のSTABLEヘルパーをSQL文ごとに評価する。現在の所属・利用状態・施設端末／個人端末・セッション確認、対象ロール、記録内容、更新・保存・競合防止の処理は変更しない。

`scripts/check-record-read-access-sql.mjs <PGliteのdist/index.js>`：1,201行の架空データで12項目。事業所別と許可なしの結果一致、匿名・書込みの拒否、版番号と全行の保持、InitPlan、再適用、想定外の既存ポリシーの上書き拒否を確認する。

本番適用は承認後、`node scripts/deploy-record-read-access.mjs --apply`。DDLのロールバック試行後に適用し、migration履歴とSELECTポリシーだけを変更する。問題時は元の条件 `alter policy records_select on public.support_records using (organization_id=public.current_organization_id());` で判定方式を戻せる（事前に現在の条件を照合する）。本番にテスト記録は作成しない。

この変更は初回データの期間制限・ページングを導入するものではなく、端末上の秒数短縮も保証しない。公開後の実際の保存・初回読み込みは「処理時間の確認」で評価する。
