# Dサポート 無料プランでの保全・権限点検

確認日：2026-10-26。実データの書き出し、復元、権限の変更、有料契約はこの確認では行っていません。

## 確認済みの更新

- 指導案の入力欄が広がり続ける現象：利用者から解消報告あり。
- Word申請通知エラー：利用者から解消報告あり。
- 管理者の二段階認証：利用者から確認済みの報告あり。回復コードはチャットやソースへ保存しない。
- 無料プランを継続する方針。有料バックアップ・追加プロジェクトを無断で契約しない。

## 無料運用でのバックアップ案

Supabase公式は、無料プランに対してCLIによる定期的なデータ書き出しと外部保管を推奨しています。
GitHubのソースコードだけでは、DB内の支援記録・職員・児童情報は復元できません。

### 何を保管するか

1. DBの構造、データ、必要なロール情報。Authを含めた対象範囲・除外を確認する。表ごとのCSVだけを完全バックアップとは扱わない。
2. Supabase Storageを利用している場合はファイル本体も別途保管。DBの書き出しにはファイル実体が含まれない。
3. アプリのソース、DB更新ファイル、Functionsのソース、設定一覧。秘密値はGitや一般共有フォルダに入れず、復旧担当者が利用できる安全な管理先へ別途保管。
4. 書き出し日時、対象プロジェクト、対象範囲、ファイル件数・サイズ・ハッシュ、成功/失敗の記録。機密本文は点検ログに載せない。

### 運用案（まだ自動設定していません）

- 業務終了後1日1回が目安。最初は担当者を決め、少なくとも大きな更新前に取得できる状態にする。
- 既存の暗号化済み事業所端末・暗号化外部媒体等へ保存し、本番と異なる場所にも複製する。個人用クラウドや公開GitHubは保管先にしない。
- 例：直近7世代＋月末3世代。これはバックアップ世代の案であり、支援記録原本の保存年限を決めるものではない。
- ファイルを作れただけで成功とせず、サイズ・終了結果・対象範囲を確認する。DBパスワードや接続文字列をチャット、画面画像、履歴へ貼らない。
- Supabase CLIの公式手順はDocker等の準備を伴う。環境と接続方法を確認してから実行する。既存のDBパスワードを確認目的で不用意にリセットしない。

## 有料環境を作らずに行う復元確認

最初は架空データを使ったローカルPostgreSQL/Supabase環境で復元手順を確認できます。
本番の書き出しを用いる試験は、個人情報を別環境へ複製するため、保管先・閲覧者・削除方法を決めてから別途承認します。

1. 本番とは別のローカル環境を用意する。外部公開せず、外部へのメール、Webhook、定期処理、外部API呼び出しを停止する。必要に応じて通信を遮断する。
2. 本番接続情報が設定されていないことを確認する。復元先をホスト名・DB名まで確認し、本番へ復元コマンドを実行しない。
3. 架空データで構造→データ等の公式順序を確認。実バックアップを用いる場合は、件数、履歴、認可、ファイルとDBの対応を点検する。
4. Auth、Storage、Functions、秘密値など、DBのみでは再現できないものを区別し、復旧できなかった項目も記録する。
5. 試験後は、保持方針に従って隔離データを片付ける。本番の履歴・アカウントには変更を加えない。

無料継続は可能ですが「バックアップ作成・復元試験が実施済み」とはまだ確認していません。ローカル環境に必要なソフトウェア・媒体は各利用条件と空き容量を確認します。

### 2026-10-26の準備結果

利用者の指定により、保存先が決まるまで実データは書き出しません。`scripts/check-backup-readiness.ps1` で前提条件のみを点検できます。現端末ではPATH上にDocker / pg_dump / psqlが見つからず、暗号化状態も現権限では確認できませんでした。

`scripts/check-backup-rehearsal.mjs --pglite <ローカルランタイム>` では、ネットワークなし・メモリ内の架空DBについて、アーカイブから別DBへの復元、記録・版番号・下書きの保持、事業所分離、匿名閲覧拒否、破損検出を9項目確認しました。これはPGliteのアーカイブ試験であり、Supabase CLIの本番バックアップやAuth・Storage等の完全復旧が済んだことを意味しません。

## 不要な管理権限・招待・トークンとは

| 対象 | 権限でできること | 整理する例 |
| --- | --- | --- |
| Dサポートの管理者・児発管等 | 職員、児童、記録などアプリ内の管理 | 退職者、兼務終了者、必要以上の管理権限 |
| GitHubの共同管理者・連携アプリ | プログラム変更、公開等（付与権限による） | 作業終了した外部開発者、使っていない連携、承認前の古い招待 |
| Supabaseの組織メンバー | DB・設定の管理等（付与権限による） | 不要な共同管理者、誤った宛先や不要になった招待 |
| 個人アクセストークン | 管理ツールが本人の代わりに操作 | 古いPC・試験用・利用目的が分からないトークン |

トークンは「管理ツール用の鍵」です。二段階認証を設定していても、有効な鍵の権限は別途点検します。
GitHub公開リポジトリは共同管理権限を外しても一般公開部分を閲覧できます。読み取り公開と変更・公開権限を分けて考えます。

### 確認手順

1. 点検表を作る：アカウント/連携名、用途、担当者、必要な権限、最終利用の分かる範囲、継続/要確認/停止候補。トークンの値そのものは記載しない。
2. Dサポート：「職員・アカウント管理」と「権限割り振り」で在籍・役職・許可を照合する。記録の作成者情報を保持するため、職員を闇雲に物理削除しない。
3. GitHub：対象リポジトリ→Settings→Collaborators（またはCollaborators and teams）。必要な共同管理者と未承認の招待を照合する。
4. GitHub本人設定→ApplicationsでAuthorized OAuth Apps / GitHub Appsを確認する。Developer settings→Personal access tokensで用途・期限・利用状況を確認する。
5. Supabase：対象組織のTeam / Membersでメンバー・招待を確認する。Account→Access Tokensで管理用トークンの用途を確認する。
6. 用途不明な鍵は直ちに削除せず、開発用CLI・自動公開・バックアップ・連携のどこで使用しているかを先に確認する。
7. 必要な鍵を交換する場合、新しい鍵を利用先へ設定→接続・公開等の動作確認→古い鍵を失効、の順で行う。漏えいが疑われる場合は別途緊急対応する。
8. 最後に、Dサポートのログイン、読み込み、保存、公開処理が動くことを確認する。不要な招待・権限の解除は対象を確定してから行う。

### 勝手に削除しないもの

- 現在の所有者・唯一の管理者。自分を外して管理不能にしない。
- GitHub CLI/Codex等で現在利用中の認証、公開用のActions設定。
- Supabaseのアプリ用公開キー（anon/publishable）と、サーバー専用の秘密キー（service_role/secret）。個人アクセストークンとは別物。公開キーが見えることだけを理由に無効化しない。秘密キーはブラウザー・チャット・Gitに出さない。
- 児童・職員の履歴、Auth、学習アカウント。権限点検のために既存の本人情報を移動・統合しない。
